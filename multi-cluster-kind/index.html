Istio Ambient Multicluster on kind

Run the Istio Ambient multicluster workshop locally — two kind clusters (east + west) with MetalLB for LoadBalancer IPs, no cloud account needed. Based on Ram Vennam's ambient-multicluster-workshop with kind-specific wiring.

kind Istio Ambient MetalLB ztunnel L4/L7 policy

This guide adapts Ram Vennam's ambient-multicluster-workshop to run entirely on your laptop. Instead of cloud-managed clusters you get two kind clusters with non-overlapping pod/service CIDRs, and instead of a cloud LoadBalancer you get MetalLB serving IPs from the kind Docker bridge network.

The repo contains setup scripts for the kind-specific parts (cluster creation + MetalLB). After those run you follow the upstream workshop steps as-is.

What you'll build

Architecture

  │  svcs: 10.96.0.0/16      │   (MetalLB LB IP)        │  svcs: 10.97.0.0/16      │

  │                          │                          │                          │
  │  ztunnel (DaemonSet)     │                          │  ztunnel (DaemonSet)     │
  │  istiod (control plane)  │                          │  istiod (control plane)  │
  └──────────────────────────┘                          └──────────────────────────┘
         │                                                       │

IP layout

ClusterPod CIDRService CIDRMetalLB pool
$CLUSTER1 (kind-east) 10.10.0.0/16 10.96.0.0/16 172.22.255.200 – 210
$CLUSTER2 (kind-west) 10.20.0.0/16 10.97.0.0/16 172.22.255.220 – 230

All MetalLB IPs sit in the kind Docker bridge network (172.22.0.0/16) well above the kind node IPs (172.22.0.2–9). This means east-west gateway LoadBalancer IPs are reachable from both clusters without any extra routing.

Setup

STEP 01

Clone both repos

Clone this repo (kind-specific scripts) and Ram's workshop side by side — you'll be switching between them throughout the lab:

# Kind-specific setup scripts (this guide)
git clone git@github.com:tjorourke/tjorourke.github.io.git
cd tjorourke.github.io/multi-cluster-kind

# Upstream workshop (open alongside this guide)
git clone https://github.com/rvennam/ambient-multicluster-workshop

You'll run the kind scripts first (Steps 2–3 below), then follow Ram's workshop with the fixes documented in the "Workshop fixes for kind" section.

STEP 02

Set cluster variables, then create the clusters

Set these first — both scripts read them, and so does the entire workshop:

export CLUSTER1=kind-east
export CLUSTER2=kind-west

Now create both clusters. The script reads $CLUSTER1 and $CLUSTER2, strips the kind- prefix to get the cluster name, and looks up the matching config in kind/.

./scripts/01-clusters.sh

Expected output — two new contexts in ~/.kube/config:

  ✓ cluster 'east' ready
  ✓ cluster 'west' ready

Contexts:
*  kind-east   ← $CLUSTER1
   kind-west   ← $CLUSTER2
STEP 03

Install MetalLB and configure IP pools

Replaces the cloud LoadBalancer. MetalLB v0.14.9 is installed on both clusters. Non-overlapping IP address pools let both east-west gateways get stable IPs reachable from both clusters. 

./scripts/02-metallb.sh

Expected output:

  ✓ MetalLB installed
  ✓ controllers ready
  ✓ pools applied

LoadBalancer services:
  east  ...   (none yet — they appear after Istio installs the east-west GW)
  west  ...   (none yet)
Why MetalLB? cloud-provider-kind has a macOS bug where it fails to write the assigned IP back to status.loadBalancer.ingress. MetalLB works reliably.
STEP 04

Set cluster env vars, then follow the upstream workshop

These should already be set from Step 2. If you've opened a new terminal, re-export them: 

export CLUSTER1=kind-east
export CLUSTER2=kind-west

Switch into the workshop directory you cloned in Step 1: 

cd ambient-multicluster-workshop

The workshop covers:

  • Installing Istio in ambient mode on both clusters
  • Setting up a shared root CA + per-cluster intermediates
  • Creating east-west gateways (MetalLB will assign IPs automatically)
  • Enabling cross-cluster endpoint discovery
  • Deploying the Bookinfo sample app across both clusters
  • Verifying cross-cluster traffic with ztunnel L4 and waypoint L7 policy
  • Egress gateway policy
  • Bring a VM into the mesh

Workshop fixes for kind

The upstream workshop README is mostly correct, but two sections need adjustments when running on kind. Replace the commands listed below when you reach those sections.

Egress Gateway — add --context=$CLUSTER1 to every command

The workshop's egress section says "This section will only use $CLUSTER1" but then omits --context from all six kubectl calls. Use these replacements:

REPLACE

Create the egress namespace

kubectl --context=$CLUSTER1 create namespace istio-egress
REPLACE

Deploy the egress Gateway

kubectl --context=$CLUSTER1 apply -f - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: egress-gateway
  namespace: istio-egress
spec:
  gatewayClassName: istio-waypoint
  listeners:
  - name: mesh
    port: 15008
    protocol: HBONE
    allowedRoutes:
      namespaces:
        from: All
EOF
REPLACE

Label the namespace to use the egress gateway

kubectl --context=$CLUSTER1 label ns istio-egress istio.io/use-waypoint=egress-gateway
REPLACE

Create ServiceEntry + DestinationRule for httpbin.org

kubectl --context=$CLUSTER1 apply -f - <<EOF
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: httpbin.org
  namespace: bookinfo
  labels:
    istio.io/use-waypoint: egress-gateway
    istio.io/use-waypoint-namespace: istio-egress
spec:
  hosts:
  - httpbin.org
  ports:
  - number: 80
    name: http
    protocol: HTTP
    targetPort: 443
  resolution: DNS
---
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: httpbin.org-tls
  namespace: bookinfo
spec:
  host: httpbin.org
  trafficPolicy:
    tls:
      mode: SIMPLE
EOF
REPLACE

Apply the AuthorizationPolicy

kubectl --context=$CLUSTER1 apply -f - <<EOF
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: ratings-to-httpbin
  namespace: bookinfo
spec:
  targetRefs:
  - kind: ServiceEntry
    group: networking.istio.io
    name: httpbin.org
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/bookinfo/sa/bookinfo-ratings"]
EOF
REPLACE

Test from ratings (allowed) and reviews (blocked)

# Should succeed — ratings is allowed
kubectl --context=$CLUSTER1 exec -it \
  $(kubectl --context=$CLUSTER1 get pod -l app=ratings -n bookinfo -o jsonpath='{.items[0].metadata.name}') \
  -n bookinfo -- curl -s httpbin.org/get

# Should be blocked — reviews is not in the allow list
kubectl --context=$CLUSTER1 exec -it \
  $(kubectl --context=$CLUSTER1 get pod -l app=reviews -n bookinfo -o jsonpath='{.items[0].metadata.name}') \
  -n bookinfo -- curl -s httpbin.org/get

BOOTSTRAP_TOKEN fix

The token embedded inside the value that istioctl bootstrap generates does not carry the istio-ca audience that ztunnel requires for authentication on kind clusters. The symptom is ztunnel starting but immediately failing to connect to istiod with an "invalid audience" error.

Root cause: The BOOTSTRAP_TOKEN is a double-base64 wrapped JSON envelope. The inner token field is a Kubernetes service account token whose audience was not set to istio-ca at generation time. kind's API server does not use the same audience defaulting as managed cloud clusters.
WORKAROUND 1

Generate the bootstrap token

Run this on your local machine (not inside the VM container). Make sure the vm1 namespace and service account exist first:

kubectl --context=$CLUSTER1 create namespace vm1
kubectl --context=$CLUSTER1 create serviceaccount vm1 -n vm1

istioctl --context=$CLUSTER1 bootstrap --namespace vm1 --service-account vm1

Copy the value of BOOTSTRAP_TOKEN from the output.

WORKAROUND 2

Decode the token envelope and inspect it

The token is base64-encoded JSON. Decode it to see the embedded fields:

echo "$BOOTSTRAP_TOKEN" | base64 -d | python3 -m json.tool

You'll see a structure like:

{
  "token": "<base64-encoded-inner-token>",
  "ca_cert": "...",
  "proxy_config": { ... }
}

The inner token field is itself base64-encoded. Decode it to confirm it lacks the istio-ca audience:

echo "$BOOTSTRAP_TOKEN" | base64 -d | python3 -c \
  "import json,sys,base64; d=json.load(sys.stdin); print(base64.b64decode(d['token']).decode())"
WORKAROUND 3

Generate a replacement token with the correct audience

Create a new token for the vm1 service account with istio-ca as the audience and a 24 h duration:

NEW_TOKEN=$(kubectl --context=$CLUSTER1 create token vm1 \
  -n vm1 \
  --audience istio-ca \
  --duration 24h)
WORKAROUND 4

Patch the token envelope and re-encode

Replace the inner token field with the new token, then re-base64 the entire envelope. Save it to a shell variable you can paste into the VM container:

# Replace token field and re-encode
PATCHED_BOOTSTRAP_TOKEN=$(echo "$BOOTSTRAP_TOKEN" | base64 -d | python3 -c "
import json, sys, base64
d = json.load(sys.stdin)
import os
new_tok = os.environ['NEW_TOKEN']
d['token'] = base64.b64encode(new_tok.encode()).decode()
print(json.dumps(d))
" NEW_TOKEN="$NEW_TOKEN" | base64 | tr -d '\n')

echo "PATCHED_BOOTSTRAP_TOKEN=$PATCHED_BOOTSTRAP_TOKEN"
WORKAROUND 5

Use the patched token when running ztunnel on the VM

Use PATCHED_BOOTSTRAP_TOKEN wherever the workshop says BOOTSTRAP_TOKEN. See the mock-VM section below for the full ztunnel run command.

Adding a mock VM (Docker)

The upstream workshop expects a real VM reachable on the network. On kind, we simulate this with a Docker container attached to the kind bridge network — it behaves identically from Istio's perspective: it gets an IP on the shared Docker bridge, ztunnel runs inside it, and the mesh sees it as a VM workload.

No scripts here. Follow each step manually so you understand what each command does — that understanding matters when adapting this to real VMs.
VM STEP 1

Create the Kubernetes namespace and service account for the VM

The VM will authenticate to istiod using a token bound to this service account.

kubectl --context=$CLUSTER1 create namespace vm1
kubectl --context=$CLUSTER1 create serviceaccount vm1 -n vm1
VM STEP 2

Build the mock-VM Docker image

We need an Ubuntu container with Docker installed (ztunnel runs as a container inside the "VM"). The --privileged flag is required so dockerd can run nested inside the container.

Save this as Dockerfile.vm:

FROM ubuntu:22.04
RUN apt-get update -qq && \
    apt-get install -y -qq curl ca-certificates iproute2 iputils-ping dnsutils && \
    curl -fsSL https://get.docker.com | sh && \
    rm -rf /var/lib/apt/lists/*

Build it:

docker build -t vm-with-docker -f Dockerfile.vm .
VM STEP 3

Run the mock VM container on the kind network

Attaching to the kind Docker bridge puts this container on the same L2 segment as the kind nodes. MetalLB IPs are reachable directly — no extra routing needed. 

docker rm -f vm1 2>/dev/null || true

docker run -d \
  --name vm1 \
  --network kind \
  --privileged \
  --hostname vm1 \
  vm-with-docker \
  sh -c "dockerd --storage-driver=vfs > /var/log/dockerd.log 2>&1 & sleep infinity"

Verify the container is running and has an IP on the kind network:

docker inspect vm1 --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'

You should see an IP in the 172.22.0.0/16 range.

Now wait for dockerd to finish its startup sequence inside the container before proceeding — it takes a few seconds on first run. Poll until docker info succeeds: 

docker exec vm1 sh -c 'until docker info >/dev/null 2>&1; do echo "waiting for dockerd..."; sleep 2; done && echo "dockerd ready"'
Why --storage-driver=vfs? Nested Docker (Docker running inside a Docker container) can't use the default overlay2 driver because the outer container's filesystem isn't a real block device. vfs is slower but works everywhere — it copies the entire layer on each write. For a demo VM this is fine. If you see failed to start daemon: error initializing graphdriver: driver not supported in the logs, check that --storage-driver=vfs is present.

Check the dockerd log if anything looks wrong:

docker exec vm1 cat /var/log/dockerd.log | tail -20
VM STEP 4

Generate and patch the bootstrap token

Follow the BOOTSTRAP_TOKEN fix section above to generate PATCHED_BOOTSTRAP_TOKEN. Then set it in your shell before the next step.

VM STEP 5

Shell into the VM and start ztunnel

Open a shell inside the mock VM:

docker exec -it vm1 bash

Inside the container, set the patched token and run ztunnel. ztunnel needs --network=host so it can intercept traffic on the VM's own network interfaces. ALWAYS_TRAVERSE_NETWORK_GATEWAY=true tells it to route traffic through the east-west gateway rather than trying a direct pod-to-pod path. 

# Inside vm1 container:
export BOOTSTRAP_TOKEN="<paste PATCHED_BOOTSTRAP_TOKEN here>"

docker run -d \
  --name ztunnel \
  --network host \
  --privileged \
  -e BOOTSTRAP_TOKEN="${BOOTSTRAP_TOKEN}" \
  -e ALWAYS_TRAVERSE_NETWORK_GATEWAY=true \
  us-docker.pkg.dev/gloo-mesh/istio-e6283d67ad60/ztunnel:1.29.0-solo-distroless

Check ztunnel logs to confirm it connected to istiod:

docker logs ztunnel 2>&1 | grep -E 'connected|error|WARN' | head -20

A successful startup looks like:

INFO ztunnel::proxy: connected to istiod at 172.22.255.200:15012
INFO ztunnel::proxy: xds connection established
VM STEP 6

Test connectivity from the VM into the mesh

Still inside the vm1 container, set the SOCKS5 proxy that ztunnel exposes on port 15080 and curl a mesh service: 

# Inside vm1 container:
export ALL_PROXY=socks5h://127.0.0.1:15080

# Standard Kubernetes DNS name
curl productpage.bookinfo:9080/productpage

# Mesh-internal global hostname (if productpage is labelled solo.io/service-scope=global)
curl productpage.bookinfo.mesh.internal:9080/productpage

Both should return the Bookinfo HTML. The first uses the Kubernetes ClusterIP; the second routes through the east-west gateway to whichever cluster is serving productpage.

Verify in the mesh: check ztunnel logs on $CLUSTER1 to confirm mTLS HBONE is being used — you should see src.identity set to the vm1 service account SPIFFE URI. 
kubectl --context=$CLUSTER1 -n istio-system logs ds/ztunnel | grep vm1
VM STEP 7

Enrol the VM in a WorkloadEntry (optional)

To make the VM a named, policy-addressable workload in the mesh, create a WorkloadEntry on $CLUSTER1. Replace VM_IP with the IP from VM STEP 3. 

VM_IP=$(docker inspect vm1 --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}')

kubectl --context=$CLUSTER1 apply -f - <<EOF
apiVersion: networking.istio.io/v1
kind: WorkloadEntry
metadata:
  name: vm1
  namespace: vm1
spec:
  address: ${VM_IP}
  serviceAccount: vm1
  network: cluster1
  labels:
    app: vm1
EOF

Once enrolled, you can write AuthorizationPolicy rules that reference the vm1 service account principal — the same as any in-cluster workload.

Troubleshooting

MetalLB IPs not appearing on LoadBalancer services

Check the MetalLB controller and speaker pods are running:

kubectl --context=kind-east -n metallb-system get pods
kubectl --context=kind-west -n metallb-system get pods

If the speaker pods have permission errors, re-apply the IP pools:

kubectl --context=kind-east apply -f yaml/metallb/east-pool.yaml
kubectl --context=kind-west apply -f yaml/metallb/west-pool.yaml

Clusters can't reach each other's east-west gateway IPs

Verify both MetalLB IPs are in the 172.22.255.x range and reachable from either cluster's node:

# Get the east-west GW IP on east cluster
kubectl --context=kind-east -n istio-system get svc istio-eastwestgateway -o jsonpath='{.status.loadBalancer.ingress[0].ip}'

# Curl it from a west cluster pod
kubectl --context=kind-west exec -it deploy/sleep -- curl http://<east-gw-ip>:15021/healthz/ready

ztunnel not starting

Ensure Docker Desktop has at least 6 CPU / 8 GB RAM. Check ztunnel DaemonSet status: 

kubectl --context=kind-east -n istio-system get ds ztunnel
kubectl --context=kind-east -n istio-system logs ds/ztunnel | tail -30

Tear down

kind delete cluster --name east
kind delete cluster --name west
